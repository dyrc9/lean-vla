\section{Implementation and Machine-Checked Model}
\label{sec:implementation}

\subsection{Prototype Integration}

The prototype integrates \system at the consumer/dispatch boundary of the
OpenPI $\pi_{0.5}$~\cite{pi05} runner for LIBERO-Safety on
robosuite/MuJoCo~\cite{liberosafety2026,robosuite2020,mujoco2012}.  The
policy checkpoint, policy-facing prompt, observations, and source-action
generation remain unchanged.  All policy-produced rows pass through one monitor
before the runner's sole environment-step interface; complete mediation assumes
that no alternative actuator path bypasses this boundary.

The implementation mirrors the design order.  The \lone component derives a task graph
from the protected benchmark goal, selects the current frontier from trusted
state, and evaluates the source block with the local checker.  The \ltwoa component holds
the current proposal, consumes its permission once, admits only the next source
row, and associates receipts and effect observations with the open transaction.
The \ltwob component snapshots simulator and controller state, evaluates at most two
virtual-guard configurations, restores the snapshot, and records the selected
configuration before real dispatch.  The no-trigger path performs no shadow
execution.

Across these paths, source-action identity is encoded as schema-tagged,
key-sorted, whitespace-free UTF-8 JSON over finite Python-float values and the
proposal shape presented at the protected controller boundary.  The
monitor records the trusted task decision, accepted source rows, selected
execution configurations, receipts, effects, task outcome, physical-risk
signals, and screening latency.  The identity claim does not extend to memory
bytes, array dtype or endianness, or equality of physical trajectories.

\subsection{Task and Checker Instantiation}

LIBERO-Safety tasks are described by BDDL goals.  The trusted adapter supports
six goal predicates exercised by the study.  They cover object placement,
containment, opening, closing, and two actuation states, and each expands into a
finite sequence of canonical task phases.  Privileged simulator geometry and
object/gripper state select the enabled phase at every replanning boundary.  This
is a benchmark instantiation of the trusted observation assumption, not a claim
that privileged state is available on a physical robot.

Before the paired experiment, the deterministic selector matches all 160
expected frontiers in a fixed qualification corpus.  The checker and effect
observer are separately exercised on supported findings, malformed and stale
inputs, and fail-closed cases.  These checks qualify the registered predicates
used in the evaluation; they do not establish completeness for arbitrary tasks
or hazards.

\subsection{Machine-Checked Transaction Semantics}

The Lean model~\cite{lean4} formalizes the finite relations at the core of C2.
It represents a proposal, its ordered source actions, a one-use permission,
indexed receipts, effect evidence, and legal task-phase transitions.  The
machine-checked results establish that modeled receipts refer to the authorized
row at the stated index, a consumed permission is unavailable for a second
opening, incomplete or unknown evidence cannot satisfy closure, and a modeled
phase advance requires the corresponding closed transaction.

The formal boundary is intentionally narrower than the complete system.  Lean
does not prove trusted-task selection, checker coverage, event ordering in the
runtime, simulator snapshot fidelity, continuous guard measurements, or
refinement from the prototype to the abstract model.  Those remain TCB,
implementation, and empirical obligations.  Accordingly, ``machine-checked'' in
this paper refers only to the abstract transaction and phase relations above,
not to general robot safety or an exact physical trajectory.
