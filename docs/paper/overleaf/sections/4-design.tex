\section{Design}
\label{sec:design}

\subsection{Architecture and Evidence Flow}

\system is an inline reference monitor at the consumer/dispatch boundary of an
existing \vla.  Its architecture has two alignment stages and three components.
\lone binds trusted task intent to the exact source block through
\taskassessment (C1).  \ltwo binds an admitted block to execution:
\transactionbinding preserves transaction identity and evidence (C2), and
\guardscreening qualifies state-dependent realization at the registered joint
boundary (C3).  Thus \lone addresses the intent--action gap, while \ltwoa and
\ltwob jointly address the action--execution gap.

Figure~\ref{fig:overview} shows one policy call.  The monitor first freezes the
trusted observation and current legal subtask, then invokes the policy and
assesses its source block.  An eligible block enters a one-use execution
transaction.  Each row is checked at the sole dispatch boundary; a near-boundary
row additionally passes through guard screening.  Receipts and post-dispatch
effects close the transaction before the trusted task phase can advance.  Every
stage names the same proposal and source block.

The distinction between source action and physical realization is central.  The
policy emits one source row, and \system never substitutes a second
policy-generated candidate.  \guardscreening may select a different
guard/controller configuration for that row, so the realized motion may change.
The trace records both objects: what the policy proposed and how the protected
controller realized it.

In the running example, the trusted task remains soda-to-plate while the policy
sees ``move to the farthest fixture.''  \taskassessment judges the returned
block against the soda-to-plate frontier, not the attacked instruction.
\transactionbinding ensures that any allowed rows and later effects still belong
to that assessed proposal.  If a row approaches a registered joint limit,
\guardscreening decides whether an admissible controller configuration can
realize that same row.  These are complementary decisions; none can substitute
for the other two.

\subsection{L1 Intent-to-ActionBlock Assessment}

\paragraph{Independent task anchor}
The attacked policy view cannot define what the monitor considers legal.  The
authority path instead compiles the protected task $T$ into a finite task graph
and selects the state-enabled frontier from $O_t^T$.  Each node names a canonical
skill and its entities; each edge is a legal task-phase transition.  For an
object-placement task, for example, the graph progresses through picking up the
object, moving it to the destination, placing it, and releasing it.  The
selector freezes $Z_t$ before $A_t$ arrives, so an attacked prompt cannot revise
the authority against which its own output is judged.

The selector may return more than one state-enabled possibility or may lack the
state needed to choose.  An unresolved choice yields an explicit unknown.  This
fail-closed behavior is important because the
trusted branch is the root of every later authorization claim.

\paragraph{Checker-relative block assessment}
The local checker evaluates the full ordered block against the frozen subtask,
trusted robot state, entity geometry, workspace bounds, velocity limits, and
unexpected-contact regions.  It propagates a lightweight state approximation
across the rows so that a block is judged as a sequence rather than as unrelated
commands.  Its output is a finite set of findings together with a known or
unknown status.

The findings have deliberately different semantics.  A covered hard risk
rejects the block before dispatch.  Covered cases include malformed input,
stale state, a workspace exit, excessive commanded motion, unexpected contact,
and unsupported evidence.  A task-progress mismatch is advisory because a legal trajectory may
temporarily move away from its target.  An advisory neither certifies completion
nor advances the trusted phase; the next proposal is assessed again against the
unchanged phase unless post-dispatch evidence independently establishes a legal
transition.  An allow decision means only that the exact source block is
eligible under the registered checker at the current state.

\subsection{L2 ActionBlock-to-Execution Alignment}

\subsubsection{L2a Transaction Binding}

An eligible assessment matters only if execution still refers to the assessed
block.  \transactionbinding therefore turns the current proposal into a
short-lived transaction.  Its contract states which evidence must be observed,
which outcomes are forbidden, and what completion evidence is required before
the task phase may change.  A fresh permission names the proposal, trusted
context, assessment, contract, and ordered source block, and can open exactly
one transaction.

Once opened, the sole dispatch boundary accepts only the next row of that block.
Each accepted row produces a receipt naming its position, source action, and
execution configuration.  The effect observer then associates the corresponding
post-dispatch observation with that receipt.  The transaction closes only after
the required ordered prefix and effect window are complete.  A legal task-graph
edge can advance only when the closed evidence also shows the associated task
completion.

This ordering makes the security consequences of failure explicit.  A stale or
replayed permission cannot authorize a new proposal; a substituted or reordered
row does not match the open transaction; missing or cross-proposal evidence
cannot close it; and an unclosed transaction cannot advance trusted task state.
Suppression may halt progress, but it cannot be reinterpreted as aligned
execution.

\subsubsection{L2b State-Conditioned Guard Screening}

Preserving source-action identity does not establish how that action will
realize near a physical constraint.  When any registered joint-side margin
falls within the trigger region, \guardscreening evaluates a bounded set of
temporary virtual-guard configurations before allowing the next row to reach
the controller.  These configurations are not new policy actions.  They are
alternative controller constraints applied to the same source row.

Every evaluated configuration begins from the same protected pre-step snapshot.
The monitor applies the source row in a one-step shadow execution, records the
predicted margins and force proxy, restores the snapshot, and verifies the
restoration before considering the next configuration or the real dispatch.
Using a common snapshot prevents one candidate's shadow execution from changing
the state seen by another candidate or by the final action.

The evaluated instantiation triggers at a minimum joint-side margin of
$0.30$ rad and considers at most two configurations.  A candidate must preserve
the identity of the source row and controller configuration, restore the
pre-step state, pass the controller audit, predict at least $0.15$ rad of margin
on all fourteen joint sides, and keep the registered force proxy at or below
10,000.  The first qualifying configuration in the fixed priority order is
selected and recorded.  If neither qualifies, \system fails closed without
actuator dispatch.  Predicted values justify the predispatch choice; realized
margins and effects remain post-dispatch evidence.

\subsection{End-to-End Procedure and Failure Semantics}

For each policy call, \system executes the following lifecycle.  It captures the
trusted task state and observation, selects and freezes $Z_t$, invokes the
policy once, and assesses the returned source block.  A hard or unknown decision
ends the proposal without dispatch.  An eligible proposal receives a contract
and one-use permission.  Each row must be the next row of that proposal; if the
joint trigger fires, the row and an explicitly selected controller configuration
must qualify before dispatch.  Receipts and effects then close the transaction.
Only closed completion evidence permits a legal task-phase advance.

The trace distinguishes four outcomes that would otherwise be easy to conflate.
A \emph{checker rejection} is a C1 decision about the registered assessment.  An
\emph{integrity rejection} is a C2 mismatch or incomplete transaction.  A
\emph{guard refusal} is a C3 failure to find a qualifying execution
configuration.  An \emph{aligned completion} is a transaction-and-phase outcome
that requires both transaction closure and observed phase completion.  The
episode-level task-success metric and physical-risk measurements are reported
separately from all four outcomes.
