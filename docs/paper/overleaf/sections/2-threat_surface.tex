\section{Background and Motivation}
\label{sec:background}

\subsection{Action-Only VLA Interface}

Our concrete path uses the OpenPI implementation of $\pi_{0.5}$~\cite{pi05}
with LIBERO-Safety~\cite{liberosafety2026}.  The policy consumes base and wrist
RGB, end-effector position and axis--angle orientation, gripper state, and a
task prompt.  It returns a $10\times7$ \actionblock: each row contains a 3-D
translation delta, a 3-D rotation delta, and a gripper command.  The runner
executes all ten rows before requesting the next block.

The full $\pi_{0.5}$ training system uses semantic signals, and language action
hierarchies can be useful control abstractions~\cite{pi05,rth2024}.  The
deployed \texttt{pi05\_libero} consumer interface, however, exposes only the
numeric block.  We therefore assume the minimum interface common to
action-only deployment: even a known and immutable checkpoint may receive
attacked context, and any self-reported explanation would share that context.
The source block is an untrusted proposal until the consumer authorizes it.

\subsection{Where Existing Protection Stops}

Two security literatures meet at the \actionblock but do not protect the same
edge.  On the authorization side, structured prompting, alignment, and trusted
agent-control-flow systems separate instructions from untrusted data or derive
digital actions from a protected query~\cite{struq2025,secalign2025,camel2026,
ace2026}.  VLA-specific systems score or select action candidates against a
plan or learned instruction--action representation
~\cite{sealvla2026,covervla2026}.  These approaches can strengthen an upstream
checker, but they do not by themselves bind the chosen continuous command to
actuator receipts and effects.

On the realization side, CPS integrity systems attest software control/data
flow, and robot-trajectory systems compare measured motion with a given
intended path~\cite{diat2019,cfaplus2024,arto2026,tat2026}.  Their integrity
roots are stronger than our software monitor, but they assume that the command,
program, or intended path is already the right object to protect.  An
action-only VLA provides no such trusted path.  A complete chain therefore
needs a bridge: trusted task $\rightarrow$ exact online proposal $\rightarrow$
actual execution evidence.

\subsection{Four Design Challenges}

Closing the two gaps creates four concrete challenges.  \textbf{C1: external
authority.}  Because the policy-facing prompt and any model explanation can be
attacked together, the current legal task stage must come from a separately
protected source.  \textbf{C2: semantic-to-continuous mismatch.}  One subtask
admits many valid trajectories.  A proxy checker that rejects every uncertain
trajectory destroys utility; one that treats uncertainty as proof creates
false allows.  \textbf{C3: execution identity.}  An approved block can still
be substituted, reordered, replayed, or paired with evidence from another
proposal.  \textbf{C4: state-dependent containment.}  The same block may be
benign in one joint state and cross a limit in another, yet rewriting the block
would invalidate the assessment and authorization object.

These challenges imply one ordered decomposition rather than four independent
filters.  The trusted branch must freeze authority before inference; L1 must
state a checker-relative verdict over the exact block; L2a must preserve that
identity through an execution transaction; and L2b may constrain the
controller near a covered boundary only without pretending that a different
policy action was assessed.
